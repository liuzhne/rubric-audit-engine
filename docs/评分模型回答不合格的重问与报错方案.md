# 评分模型回答不合格的重问与报错方案

> 状态：**已确认并实现**（维护者 2026-11-12 确认，第 10 节六个问题都按推荐）。实现与方案的出入见第 12 节。
>
> 分支：`claude/scoring-invalid-output-retry`（基于 develop `baaa77a`）。

## 1. 起因

2026-11-12 12:32，生产（main `92f4b02`，Vertex `google/gemini-2.5-flash`，思考关闭）上的评分任务「助手评分 · 11-12 12:31 · 1 份」整篇失败，页面显示：

> 评分规则执行失败；请查看规则任务错误码或 Worker 安全日志后重试。

只读查到的事实：

- 6 小时内只有一条规则失败：评分项 `T03` 的规则 `t03.v1`，日志为 `rule_execution_failed … error_code=RULE_EXECUTION_FAILED exception_type=ValueError`。
- 失败前 1 毫秒，这条规则的模型调用正常返回：`finish_reason=stop`，输出 33 token，没有思考、没有截断。
- 其余规则全部判完，本篇共花输入约 9.3 万 token、输出 3683 token。期间 7 次 429 都由 HTTP 层自动重试成功，与失败无关。

也就是说：模型答了，答案没有通过我们的校验，校验抛出 `ValueError`。具体是哪一条校验，现有日志查不出来（见 2.2）。

## 2. 现状与缺口

### 2.1 回答不合格不重试

模型回答要过两道校验，都按「有疑问就拒绝」设计：

| 位置 | 做法 | 不合格时 |
|---|---|---|
| 适配器：`llm/core_view.py` 的 `decode_core_response`、`llm/core_adapter.py` 的 `normalize_core_provider_response` | 字段不全、状态不在清单里、非触发却带了判定、触发却没有证据、引用了不存在的证据编号等，直接 `raise ValueError` / `TypeError` | 被执行器的总兜底接住，记成 `RULE_EXECUTION_FAILED` |
| 执行器：`scoring/core/rule_executor.py` 的 `_semantic_decision_core`、`_semantic_occurrences` | 返回稳定错误码：`RULE_DECISION_INVALID`、`REQUIRED_EVIDENCE_INVALID`、`BAND_SELECTION_INVALID`、`FINDING_CODE_NOT_AUTHORIZED`、`UNKNOWN_RULE` | 判定记为 `invalid` |

两条路的结果一样：规则任务记为 `failed_exhausted`，评分项不出分，总分为空，整篇算失败（D-016）。

对比同一个系统里的其它情况：

- 429、超时、5xx：HTTP 层最多试 3 次。
- 评分标准侧的 AI 任务（起草、归类、审查、适用范围）：输出不合格时带修正提示再执行 1 次（`ai_tasks/execution.py` 的 `repair`）。
- 评分路径：`rule_scoring_tasks.max_attempts` 固定写 1，代码注释写明「规则级还没有自动重试」。

所以评分路径上，模型一次偶发的格式失误，代价是整篇论文失败、老师手动重试。一份论文有上百条规则，单条出错的概率不高，但乘起来不低。

### 2.2 报错指错方向，日志定不了位

- `scoring/core/failures.py` 只认带 `code`、`error.code` 或 `reason` 的异常。适配器校验抛的是裸 `ValueError`，落到最后一支，和真正的代码缺陷共用 `RULE_EXECUTION_FAILED`。
- `batch_scoring/jobs.py` 的 `_incomplete_scoring_error` 只读规则任务的 `provider_error`；而 `persistence.py` 只给 `PROVIDER_` / `TOKEN_BUDGET_` 开头的错误码写 `provider_error`。上表两条路都没有，于是材料级报的是「评分规则执行失败」，失败类别记成 `checker`（不是 `llm`）。
- 评分助手的诊断卡片（`assistant/views.py`）把它显示成「系统错误……请把任务名称告诉管理员」。
- 日志只记异常类型。校验消息其实都是固定的英文短句，不含论文内容，却没有记下来。这次排查因此只能确定「是回答校验」，不能确定是哪一条。
- 真正的代码缺陷同样只有异常类型，没有出错位置。

## 3. 目标与不做的事

目标：

1. 模型回答不合格时，自动带修正提示重问 1 次；仍不合格才判无效。
2. 这类失败有自己的错误码和中文说明，归为模型问题；日志能看出是哪一条校验没过。
3. 真正的代码异常，日志带出错位置。

不做的事：

- 不放宽任何一条校验。重问得到的回答走同一套校验。
- 不改 D-016：重问后仍不合格的规则照旧无效，评分项不出分，总分为空。
- 不处理截断（`PROVIDER_OUTPUT_TRUNCATED`）、拒答、思考不一致：它们各有处理办法，截断恢复属于《评分输出预算与截断恢复改造方案》P2。
- 不保存模型的原始回答，不把模型回答的内容写进日志或重问请求。
- 不加迁移。

## 4. 重问

### 4.1 放在哪

放在执行器的 `_semantic_decision_for_envelope`（单条）与 `_judge_semantic_group`（互斥组）里，不放在适配器里。

- 一处实现覆盖三个适配器（Chat / Responses / Messages）和两个 Profile 的运行时。
- 两道校验（适配器抛异常的、执行器返回错误码的）在这里汇合，都能触发重问。
- 尝试次数本来就在这里记（`_record_attempt`）。

### 4.2 什么情况重问

只有「请求发出去了、模型答了、答案不合格」才重问：

- 适配器抛出新的 `CoreResponseInvalidError`（见 5.1），或 `ProviderJSONOutputError` 的 `reason` 为 `invalid_json` / `empty_content`；
- 执行器校验返回上表的 5 个错误码之一。

不重问的：截断、拒答、思考不一致、输入超预算、熔断、HTTP 错误（HTTP 层已经重试过）、请求没发出去的、判定账本里复用的旧判定校验不过的（现有逻辑已经会重新判一次）、确定性规则、以及任何别的异常。

### 4.3 怎么重问

采样温度是 0，原样重发大概率得到同样的回答。所以重问时在原请求后面追加一条固定的修正提示：

- 原请求的系统消息和用户消息一字不改，修正提示作为追加的一条用户消息。系统消息仍然是可缓存的前缀。
- 修正提示按错误类别从代码里的固定清单取，例如「上一次回复缺少必填字段或含有未声明字段。请严格按要求的 JSON 结构重新回复，五个字段都必须出现。」清单约 6 条，对应字段、状态、非触发带判定、触发缺证据、证据编号或引文不合格、档位不合格。
- **不回显模型上一次的回答**，一个字都不带：回答里可能有论文原文，也可能有注入内容。
- 运行时接口加一个可选参数：`llm_runtime.score(envelope=…, repair=<类别>)`、`score_group(…, repair=…)`。执行器先看运行时的签名里有没有这个参数，没有就不重问（Mock 与旧运行时不受影响）。

### 4.4 重问几次、花多少

- 每条规则（或每个互斥组）最多重问 1 次。
- 每篇论文最多重问 `SCORING_OUTPUT_REPAIR_MAX_PER_PAPER` 次，默认 5。超过说明是模型与输出要求系统性不合，继续重问只是花钱；之后的不合格直接判无效。设为 0 即关闭整个功能，这也是回滚办法。
- 重问走同一套计量：计入本篇输入上限（`SCORING_MAX_INPUT_TOKENS_PER_PAPER`）、用量账本和思考守卫。输入上限已用完时不重问。
- 按这次事故估算：重问一次约 2900 输入 token；不重问的代价是整篇失败后老师手动重试。

### 4.5 互斥组

互斥组的回答不合格时，整组带修正提示重问 1 次（算 1 次重问）。仍不合格，组内各档照旧全部无效，不拆成逐条调用。

理由见第 9 节。

### 4.6 判定身份与账本

- 第一次请求与现在逐字节相同，所以判定身份不变，`CORE_PROVIDER_PROMPT_VERSION` 不升，现有账本条目全部继续有效。
- 重问得到的合格判定照常写进判定账本，以后同一身份直接复用。
- 修正提示清单有自己的版本号 `OUTPUT_REPAIR_VERSION`，只写进日志，不进身份。
- 这是一个明知的代价：账本里会有少量「第一次不合格、提示后才合格」的判定，按身份重放时模型第一次可能仍答不合格。可追溯性靠规则任务的尝试次数和日志保证（4.7）。

### 4.7 记录

- 规则任务：重问过的规则 `attempt_count=2`、`max_attempts=2`；没重问的保持 1。`record_provider_attempt` 从「记 0 或 1」改为累加。
- 日志新增一行 `rule_output_repair rule_code=… check=… repair_version=… outcome=accepted|rejected|skipped_cap`，不含任何正文。
- 不加列：哪一条校验没过只进日志。要在界面上长期展示再考虑加列（Q6）。

## 5. 报错

### 5.1 新错误码

- 新增 `CoreResponseInvalidError(ProviderJSONOutputError)`：`reason="output_invalid"`，另带 `check`（固定的短标识，如 `fields`、`status`、`non_triggered_has_decision`、`triggered_without_evidence`、`unknown_evidence_ref`、`level`、`finding_code`、`quote`）。它仍是 `ValueError` 的子类，现有的 `except (TypeError, ValueError)` 不受影响。
- `core_view.py` 与 `core_adapter.py` 里针对模型回答的裸 `ValueError` / `TypeError` 全部换成它。针对我们自己输入的检查（例如「互斥组至少两条规则」）不换，那些是代码问题。
- `failures.py` 增加一支：`reason == "output_invalid"` → `PROVIDER_OUTPUT_INVALID`，消息为 `semantic provider output failed validation (check=<标识>)`。
- 以 `PROVIDER_` 开头，`persistence.py` 现有逻辑会自动写进规则任务的 `provider_error`，材料级随之归为 `llm`。

### 5.2 执行器返回的 5 个错误码

错误码本身不改（已保存的结果、人工复核任务和回放校验都在用）。只改一处：语义规则、且确实发过请求时，`persistence.py` 也把这 5 个码写进 `provider_error`，让材料级能看到根因。「规则类型不支持」这类没有发请求的情况不写。

### 5.3 材料级说明

`jobs.py` 的 `_incomplete_scoring_error` 增加一支，覆盖 `PROVIDER_OUTPUT_INVALID` 与上面 5 个码，统一报 `PROVIDER_OUTPUT_INVALID`：

> 模型对部分规则的回答没有通过格式校验。可以直接重试失败项，已成功的规则会复用；反复出现请换一个模型。

（#103 复审后改为中性措辞：上限为 0 或名额用完时并没有重问，不能写「已自动重问」。）

`assistant/views.py` 的诊断卡片加对应一条，标题「模型回答不合格」，不再让老师去找管理员。

### 5.4 真正的代码异常

`RULE_EXECUTION_FAILED` 保留给其余异常。日志在 `exception_type` 之外加 `where=<模块>:<行号>`，取调用栈里最靠内的本项目代码帧。只有位置，没有异常消息和变量值，不会带出论文内容。页面文案不变。

## 9. 放弃了什么

- **原样重发**：温度为 0，同一请求大概率得到同一个不合格回答，白花一次调用。
- **把模型上一次的回答连同错误一起发回去让它改**：修正效果可能更好，但回答里可能带论文原文或注入内容，再次进入请求等于让模型输出影响下一次输入；固定清单足以说明哪里不对。
- **放宽校验，自动补齐缺的字段**（例如缺 `occurrences` 就当空数组）：等于替模型做判定，违背「每个扣分都带证据」和有疑问就拒绝。
- **在适配器里重问**：三个适配器各写一遍，而且覆盖不到执行器那一道校验。
- **互斥组不合格后拆成逐条调用**：一个 5 档的组要多 5 次调用，而且逐条判定失去了「组内只选一档」的约束；截断恢复方案里拆组是因为容量不够，这里不是容量问题。
- **重问后仍不合格就让老师直接打分**：要放宽 D-016，此前已决定暂不做。
- **升 `CORE_PROVIDER_PROMPT_VERSION`**：会让现有判定账本全部失效，而首次请求一个字都没变。
- **加一张尝试明细表**：这次只需要次数和日志；真要在界面上展示每次尝试再加。
- **把校验消息原文记进日志**：消息目前都是固定短句，但以后有人往里拼变量就可能带出内容；改记固定的 `check` 标识。

## 12. 实施记录（2026-11-12）

按方案实现，测试见 `backend/app/tests/test_scoring_output_repair.py`。与方案的出入：

- **每篇上限由运行时给出**：执行器读 `llm_runtime.output_repair_limit`，由两个 Profile 的运行时去读 `SCORING_OUTPUT_REPAIR_MAX_PER_PAPER`，内核不读配置。运行时按评分器 `score_core_envelope` 的签名判断接不接受 `repair`，方案 4.3 写的是「执行器看运行时的签名」。
- **Messages 协议不是追加一条消息**：该协议要求用户与助手交替，修正提示放在同一条用户消息的第二个文本块里。Chat 与 Responses 是追加一条用户消息。原文都不改。
- **`RULE_EXECUTION_FAILED` 的出错位置也写进了复核说明**，不只在日志里（只有模块与行号）。
- **`OUTPUT_REPAIR_VERSION` 目前没有写进日志行**：`rule_output_repair` 只有 `rule_code`、`check`、`outcome`。版本号在 `llm/core_adapter.py` 里，内核不导入适配器；需要时再经运行时带出来。
- **重问请求本身失败时**：因单篇输入上限没发出的，报告第一次的不合格；其它失败（限流耗尽、熔断等）报告那次失败本身。
- 互斥组第一次答不合格、而运行时在重问时表示判不了整组（返回 `None`）的情况，按第一次的失败报告。

### #103 复审修正（2026-11-13）

- 材料级说明改为中性措辞；有没有重问过看规则任务的 `attempt_count`。
- 校验标识只认内核登记的集合 `failures.OUTPUT_REPAIR_CHECKS`，其它值一律按 `fields`。
- Responses 协议的 JSON 解析失败、缺少正文也带 `reason`，能重问。
- 回答里类型不对的字段（数组当状态、数字当 `occurrences` 等）按回答不合格处理。
- 互斥组的重问另看评分器整组入口的签名。
- 重问提示计入输入估算。
