# 扣分合计超满分封底方案（扣完为止）

状态：**已确认**（2026-11-16，维护者确认第 9 节 Q1–Q6 全部按推荐），实施见第 12 节。
起因：一篇生产论文（下称“案例 A”，批次 `28cb1d5d…`，运行 `5109f7e5…`）显示「评分规则执行失败」。
相关：`docs/AI扣分细则起草改造方案.md` 的 D7（扣分合计约束，方案暂停）；`docs/通用评分内核架构方案.md` 聚合规则第 5 条。

边界：只改 Core 聚合的扣分合计行为、它的展示和报错文案。**不改**模型请求、提示词、判定复用身份、评分策略快照、
发布校验与数据库表结构；无迁移，Alembic head 不变，不升 `PROMPT_VERSION`。

## 0. 要点

1. **问题**：一个扣分类评分项里，命中规则的扣分逐条累加，合计超过该项满分时，内核不扣到 0，而是把**整项判为无效**。
   论文因此没有总分；无效项不能普通改分；判定会被复用，**重试结果完全相同**。
2. **改法**：从满分起扣，扣到 0 为止。最后一条入账的规则只扣剩下的分，之后命中的规则记 0 分；该项正常出分，
   另记一条不阻塞的提示，说明“命中扣分合计 X 分，超过满分 Y 分，已扣至 0 分”。
3. **对分数的影响**：原来能算出分数的评分项，结果**一分不变**（合计不超过满分时两种算法相同）；
   只有原来判无效的项会从“无分”变成 0 分。
4. **已失败的论文**：上线后点「重试失败项」即可。模型判定从账本复用，不再调用模型、不计费（第 5 节说明前提）。

## 1. 现状与证据

### 1.1 这篇论文

评分标准 `b0bef184…`，模型 gemini-2.5-flash。6 个评分项里 4 项正常出分（T01 20、T02 14、T04 5、T06 20），两项无效：

| 评分项 | 满分 | 命中规则（按处理顺序，扣分额） | 发生了什么 |
|---|---|---|---|
| T03 分析与解决问题2 | 20 | #12 −10、#14 −10（余 0）、#8 −10 | 处理 #8 时不够扣 → #8 与 T03 判无效 |
| T05 分析与解决问题4 | 10 | #12 −5、#14 −3（余 2）、#18 −5、#9 −5 | 处理 #18 时不够扣 → #18 与 T05 判无效，#9 未处理 |

规则按 `rule_code` 的字符串顺序处理，所以 `#8`、`#18` 排在 `#12`、`#14` 之后。

### 1.2 代码

- `rule_executor._deduction_effects`（`rule_executor.py:1308`）：本条扣分大于剩余分数时返回 `DEDUCTION_EXCEEDS_CRITERION_MAX`。
- `_criterion_results` 的扣分循环（`rule_executor.py:1470` 起）：收到这个错误就把本条规则改成 `invalid`、
  记一条 `block` 级问题、跳出循环，整项 `status=invalid`、`contributions=[]`。
- 这个码不是 `PROVIDER_*`，所以材料级报错落成笼统的 `RULE_EXECUTION_FAILED`
  「评分规则执行失败；请查看规则任务错误码或 Worker 安全日志后重试」（`batch_scoring/jobs.py:816`），引导用户重试。
- 判定视图（`judgement_view.py:77`）把命中但没入账的规则标成「命中（已达扣分上限，未再扣分）」，看起来像正常封顶。
- 现有测试 `test_per_occurrence_runtime_overflow_is_invalid_and_never_clamped`、
  `test_multiple_rules_cannot_cumulatively_drive_criterion_below_zero`（`test_m4_rule_executor.py`）锁定的就是“判无效、不截断”。

### 1.3 为什么常见

这份评分标准每个评分项的扣分规则合计都远超满分，例如 T03 有 18 条规则、合计 174 分，满分 20 分。
老师写扣分细则的习惯就是罗列可能的问题、“扣完为止”，起草也是分批各自定分，没有人管合计（D7）。
论文写得越差，命中越多，越容易撞上——恰好是最需要分数的那一类。

### 1.4 旧路径早已封底

v1 路径的扣分制已经是 `clamp(max − Σpoints, 0, max)`：`engine.py:1718` 与 `checkers/findings_checker.py:77`。
只有 Core 是“越界即无效”。本方案让两条路径对同一种情况的处理一致。

## 2. 目标与不变量

- 扣分合计超过满分时，该项得 0 分并正常出分，不进人工复核、不阻塞总分。
- 合计不超过满分时，每条规则的扣分、每个评分项的分数、总分、等级都与现在**逐位相同**。
- 不越过 0，也不越过满分；`Σ contributions = 该项分数` 继续成立（审计可对账）。
- 不改变任何模型请求，因此不让已有判定失效（见第 5 节）。
- 规则自身的配置错误（单条 `max_points` 超过满分、矩阵非法等）仍按原样判无效；本方案只放开**运行时累计**溢出。

## 3. 改法

### 3.1 计算

在 `_criterion_results` 的扣分循环里，`_deduction_effects` 不再返回溢出错误，而是按剩余分数入账：

1. 照旧从满分起算，规则顺序照旧（见 Q3）。
2. 每条命中规则先按 `repeat_policy`（once / per_occurrence / capped）算出应扣额，再与剩余分数比较：
   - 应扣额 ≤ 剩余：全额入账（与现在相同）。
   - 应扣额 > 剩余：只入账剩余部分；`per_occurrence` 与 `capped` 按 occurrence 顺序逐个入账，扣到 0 为止，
     之后的 occurrence 记 0。
   - 剩余已是 0：本条及之后命中的规则全部记 0。
3. 每条规则额外记 `nominal_effect`（应扣额）和 `calculated_effect`（实际入账），两者不同即“被封底”。
4. 只要有一条被封底，就给该项追加一条问题 `DEDUCTION_FLOORED_AT_ZERO`，严重度 `report`（只报告，不阻塞、不进复核），
   内容只有数字：命中扣分合计、满分、实际扣分。

单条规则的 `per_occurrence` 自身累计超满分（现有测试的第一种情况）同样按第 2 步处理。

### 3.2 标记新算法

评分项上已有 `aggregation_schema_version`（现为 `criterion-aggregation@2`）。新算法写 `criterion-aggregation@3`，
读取侧把 `@3` 加进已认识的版本（`engine.py:2572`、`2618` 两处）。这样能区分一条结果是新算法算的还是旧算法算的，
而**不碰**引擎版本号和评分策略（理由见第 5 节与 Q1）。

### 3.3 展示

`judgement_view` 的标签按实际入账区分：

| 情况 | 标签 | 效果文字 |
|---|---|---|
| 全额入账 | 扣分（不变） | 扣 10 分 |
| 部分入账 | 扣分（已扣至 0 分） | 扣 2 分（原应扣 5 分） |
| 入账 0（之前已扣至 0） | 命中（该项已扣至 0 分，未再扣分） | — |

删去现有的「命中（已达扣分上限，未再扣分）」：它只在入账 0 时出现，而新算法下入账 0 只有上表第三种原因。
评分项的说明句末追加：“命中扣分合计 X 分，超过满分 Y 分，已扣至 0 分。”

### 3.4 报错文案

封底之后 `DEDUCTION_EXCEEDS_CRITERION_MAX` 不再由运行时累计产生。仍改进材料级报错：`RULE_EXECUTION_FAILED`
的文案去掉“重试”暗示，改为指出判定无效的评分项与规则（编码，不含正文），并说明不是模型调用失败、多半与规则配置或检查器有关。这些规则没有可复用的判定，重试会重新判定，但原因不消除时结果通常相同。
这一条与封底无关，单独也成立（见 Q5）。

### 3.5 不做的事

- 发布时的“扣分合计超满分”预警（D7 的 P0 部分）、起草时的每批扣分额度（D7 的 P1 根治）不在本方案；
  封底后它们从“必须修”变成“提示性”，仍可另做。

## 4. 对分数的影响

- **原来能出分的评分项**：合计不超过满分时，新旧算法的每一步入账都相同 → 分数、总分、等级逐位不变。
  因此 QWK 留出集上已有分数的样本**不受影响**，不需要为本方案调用真实模型重跑评测。
- **原来判无效的评分项**：从“无分、整篇无总分”变成 0 分、整篇有总分。这类论文的总分会出现，
  并按现有规则触发复核（例如总分低于 60 分走 `review.total_below`）。
- **区分度的代价**：同一项里，命中 3 条与命中 10 条都是 0 分。这是“扣完为止”的本义，也是 v1 路径的现状。
- **量化**：上线前可用只读脚本扫一遍生产里 `auto_score_status='invalid'` 且问题码为
  `DEDUCTION_EXCEEDS_CRITERION_MAX` 的评分项，统计会被救回的论文数（第 8 节）。这一步要在生产容器里运行，
  需要维护者授权或亲自执行；它只读库、不调用模型。

## 5. 复用与成本

规则判定账本的身份（`decision_identity.rule_decision_identity`）哈希整个模型请求信封，信封里含
`runtime_identity`（引擎版本号）与 `policy_hash`。所以：

- 若升引擎版本号（如 `thesis-core-adapter@2`）或改评分策略快照，所有已有判定都会失效，
  重试与之后的评分全部重新调用模型、重新计费。
- 本方案只改聚合、只升评分项上的 `aggregation_schema_version`，信封不变 → 判定照常复用。
  这篇论文重试时语义规则的判定全部从账本取，不发请求。

前提（实施时用测试锁住）：被溢出判无效的那条规则，它的模型判定在聚合之前已经写进账本。
从这篇论文第二次运行只有 78 个输出 token 看是成立的；实施时补一个“溢出 → 封底后重试零调用”的测试。

## 10. 放弃了什么

- **保持判无效、转人工复核**：论文仍没有总分，老师要逐项手工处理；对“扣完为止”的常见写法，这是系统制造的工作量。
- **允许负分**：违背“分数在 0 到满分之间”的不变量，也与老师的理解不符。
- **按比例缩放各条扣分**（让合计正好等于满分）：每条规则的扣分额都会偏离老师写的数字，难以解释、难以审计。
- **只在发布时拦截，强制老师改标准**：这份标准 T03 的合计是满分的 8.7 倍、T05 是 7 倍，逐条压分不现实，而且会让现有已发布的标准全部不可用。
- **只靠起草时的扣分额度根治（D7 P1）**：要调用真实模型评测，覆盖不到手写或已发布的标准；它仍值得做，但不能替代运行时的兜底。
- **升引擎版本号来标记**：见 Q1，代价是全部判定重新计费。

## 11. 风险

- **掩盖规则配置问题**：原设计用“判无效”逼出配置错误。现在由 `DEDUCTION_FLOORED_AT_ZERO` 提示保留可见性；
  单条规则自身越界仍判无效。
- **同项内区分度下降**：见第 4 节，属于有意的取舍。
- **复用前提不成立**：若溢出规则的判定没有进账本，重试会重新调用模型（只影响少数规则的费用，不影响正确性）；由第 5 节的测试锁住。

## 12. 实施情况（2026-11-16，分支 `claude/deduction-floor-at-zero`）

- 按第 6 节清单实施。`nominal_deduction_amounts` 从 `_deduction_effects` 拆出并公开，判定视图与评分项说明句用它算“原应扣”，与入账同一套算法。
- 封底提示的严重度用现成的 `info`（与“仅提示”规则相同），`rule_code` 为空；`from_core_issues` 不认识它，所以不进复核原因。
- 判定视图另加一种情况：旧结果（`@2`）里评分项是 invalid/blocked 时，命中未入账的规则显示“命中（该项未计分）”，不冒充“已扣至 0 分”。
- 测试：`test_m4_rule_executor`（per_occurrence、多条、capped 封底，合计不超满分逐位不变）、`test_scoring_usage_and_decision_ledger`（封底后重试零调用）、`test_scoring_evidence_basis`（标签、说明句、`@3`、旧结果标签）、`test_m8_batch_scoring_jobs`（报错点名规则）。
- 第 4 节的生产只读统计没有做（需要在生产容器里运行）。
