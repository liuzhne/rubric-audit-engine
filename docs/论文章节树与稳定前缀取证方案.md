# 论文章节树与稳定前缀取证方案

状态：已确认（2026-11-15，维护者确认第 12 节的 Q1–Q6 全部按推荐）。阶段 1、2 已实现（开关默认关闭，
未做 QWK），阶段 3、4 未做；实施情况与偏离见第 17 节。
本文的现状描述来自阅读代码，没有实跑验证；成本数字是按假设估算的，落地前要用真实用量重算。

## 0. 要点

1. **现状**：每条语义规则（互斥组算一条）是一次独立请求。代码先用 BM25 从全文选出前 12 段，
   压缩到合计不超过 3000 字，再交给模型判断。并没有每次把全文发给模型。
2. **真正的弱点不是 token 太多，而是全局规则看得太少**：证据靠关键词相关度选，规则用词与论文用词
   不一致时会漏掉关键段落。
3. **最左前缀没有严格执行**：只有系统提示词、概况卡、评分项三段是稳定的，证据之前还夹着随规则变化的
   `context` 与 `scope`；评分侧也没有记录缓存命中的 token 数。
4. **发现一处冲突**：适用范围开关打开后，提示词告诉模型“给出了整章”，但证据仍被压缩和截断，
   模型可能据此误判“缺失”。开关目前关闭，生产不受影响，打开前必须修。
5. **“全文在前、规则在后”不会更省**：按假设估算，即使缓存全部命中也是现在的 3 倍多。它换来的是判定
   质量，不是成本。
6. **建议按范围分层**：一章 / 多章对照的规则给整章原文并共用前缀；全局规则用“目录骨架 + 分节摘要定位
   + 原文判定”；其余规则维持现状。
7. **树不需要新存储**：论文快照里每个段落已经带标题路径，读取时用代码拼树即可。只有模型生成的摘要
   才需要另存一张表。
8. **摘要只用来定位，证据必须回到原文**：这条线不能破，否则逐字引用的防编造机制失效。
9. **借鉴“边查边读”的结构，不借鉴多轮循环**：批量评分走固定的两步；多轮自行翻阅只留给评分助手里
   人工发起的追问与重判。
10. **分四个阶段，每个阶段独立开关、独立评测**；阶段 1 改变证据集合，需要 QWK 重新锚定。

## 1. 背景

维护者提出的问题：

- 不同适用范围的规则现在怎么评、提示词怎么适配范围、怎么省 token，是否严格执行最左前缀原则；
- 能否把评测内容放在前面不变、规则放在最后，以命中厂商的前缀缓存；
- 能否把论文存成树，或者把论文当作“记忆”来压缩；
- Claude 读代码的方式是否可以借鉴。

相关方案：`docs/评分请求token压缩方案.md`（阶段 4 稳定前缀）、`docs/评分细则适用范围方案.md`（第 8 节
评分时应用范围）、`docs/论文评分第二阶段改造方案.md`。

## 2. 现状

### 2.1 一次评分怎么走

1. **解析**：论文切成证据单元（段落、表格等），每个单元带 `section_path`（各级标题）。存在
   `document_snapshots.snapshot_payload` 的 `sections` 列表里，快照不可变、按内容寻址。
2. **选证据（代码，不调用模型）**：`retrieval/selection.py`，版本 `section-bm25-diverse@2`。查询是
   “评分项名称 + 规则文字”，BM25 排序后做章节多样性调整，取前 `SCORING_EVIDENCE_TOP_K`（默认 12）段。
3. **压缩**：`retrieval/compression.py`，每段最多 400 字，合计最多 3000 字，只保留原文连续片段。
4. **模型判断**：`llm/core_view.py` 组装判断用视图，模型返回是否触发并逐字引用证据。
5. **代码校验与算分**：引用必须落在给出的片段里；分值由代码计算。

确定性规则全程不调用模型。

### 2.2 请求的构成与顺序

每条规则一次请求，请求之间没有对话历史：

```
系统提示词（同类请求逐字一致）
用户消息（JSON）：概况卡 → 评分项 → 上下文 → 范围 → 证据 → 本条规则
[重问时追加一条固定的修正提示]
```

唯一的合并是互斥组：同一缺陷的几档放进同一次请求。

### 2.3 适用范围（`SCORING_JUDGE_SCOPE_ENABLED`，默认关闭）

- 每篇论文做一次章节角色归类：先用词表，对不上的一级标题只发标题列表让模型归类。
- 一章：只在该章内取，最多 60 段；多章对照：各章交替取。
- 目标章节找不到：不调用模型，转人工。
- 提示词：系统提示词追加一段写死的范围说明；用户消息多一个 `scope` 字段，每条证据带 `section_role`。

## 3. 问题

| # | 问题 | 位置 | 后果 |
|---|---|---|---|
| P1 | “整章完整”按选中的段数算，但发给模型的证据还要压缩（每段 400 字、合计 3000 字，超出的整段丢弃） | `judge_scope._coverage_by_target`、`compression.compress_evidence` | 一章超过约 8 段时模型看到的不是整章，却被允许判“缺失” |
| P2 | 全局规则只看 BM25 选出的 12 段 | `selection._rank` | 用词不一致时漏掉关键段落；模型判“证据不足”或漏判 |
| P3 | 默认按规则选证（`SCORING_EVIDENCE_SCOPE=rule`） | `profiles/thesis.py` | 规则之间的共同前缀只有系统提示词、概况卡、评分项，很可能达不到厂商的最短缓存长度 |
| P4 | `context`、`scope` 随规则变化却排在证据前；压缩按本条规则的文字挑句子 | `core_view._view` | 即使改成共用证据，前缀仍会在证据之前或证据中间分叉 |
| P5 | 评分侧没有记录缓存命中的 token 数 | 评分用量记录 | 无法用数据判断前缀缓存是否有效 |
| P6 | 证据是孤立片段，没有前后文 | `compression` | 断章取义；模型不知道自己看到的是论文的哪一块 |

## 4. 目标与不变量

目标：

- 让模型看到的范围与提示词声明的一致（修 P1）。
- 提高全局规则的取证命中率（P2、P6）。
- 让前缀真正可缓存，并且能计量（P3–P5）。

不变量：

- 确定性优先：树、范围、取证路径由代码决定。
- 每个扣分必须逐字引用原文；模型生成的摘要不能作为证据。
- 无状态、可复现：同一篇论文、同一份规则、同一组身份，重评结果可复用。
- 模型不出分。
- 所有变化加开关，默认关闭；开关关闭时请求与现在逐字节相同。

## 5. 总体设计：按范围分层

| 规则范围 | 给模型的内容 | 共用前缀 |
|---|---|---|
| 一章 | 目录骨架 + 该章原文（按原顺序，不按规则压缩）+ 规则 | 同一章的所有规则 |
| 多章对照 | 目录骨架 + 各目标章原文 + 规则 | 目标章集合相同的规则 |
| 全局 | 目录骨架 + 分节摘要 → 定位 → 被定位小节的原文 + 规则 | 目录骨架与摘要，同一篇论文所有规则 |
| 不需要章节上下文的规则 | 维持现在的片段做法 | 目录骨架 |

请求顺序改为（越靠前越稳定）：

```
系统提示词                         全部请求共用
目录骨架（+ 分节摘要）             同一篇论文共用
章节原文 / 被定位小节的原文        同一范围的规则共用
评分项 → 上下文 → 范围 → 规则      随规则变化，全部放最后
```

## 6. 阶段 1：章节树与按子树取证

全部是代码逻辑，不调用模型。

- **拼树**：读快照时按 `section_path` 拼成内存里的树。节点编号用“标题路径 + 章节序号”，避免同名标题
  （如两个“小结”）冲突。节点只记名下段落的编号范围，正文仍从快照取。
- **目录骨架**：标题树加每节的字数、段落数、图表数，放在请求开头。只做定位用，不是证据，提示词里写明。
- **按子树取证**：范围从一级章节细到小节；整节原文按论文原顺序给出。
- **修 P1**：`coverage` 改为按**实际发出**的内容计算。整章放得进预算才标 `complete`，此时不做逐段
  压缩；放不进就在章内截取并标 `partial`。
- **相邻段落**：全文范围的规则命中一段时，带上同一小节的前后段（受预算约束）。
- **证据别名**：按论文固定编号（如按章节序号与段落序号），不再每次从 E1 重排，保证同一段在不同请求里
  的写法相同。

预算：章节原文不再受 3000 字合计上限约束，改由 `SCORING_CONTEXT_WINDOW_TOKENS` 与单独的章节预算控制，
具体数值见 Q3。

## 7. 阶段 2：稳定前缀与缓存计量

- 视图顺序按第 5 节调整，`context`、`scope` 移到正文之后。
- 共用前缀里的正文不按规则压缩。
- 执行顺序：同一前缀的第一条请求先发完，再并发其余的，避免并发时全部按全价计费。
- Schema 里随规则变化的枚举（规则编号、证据别名）是否影响前缀，按厂商核实后再决定是否放宽（Q5）。
- **计量**：评分用量记录增加缓存命中的 token 数。这是新增列，需要迁移；先做计量再判断其余改动的收益。

## 8. 阶段 3：分节摘要用于定位（把文档当记忆）

- **生成**：每篇论文解析后生成一次分层摘要（每节、每章、全文），模型调用一次或按章分几次。
- **冻结**：摘要存下来并带版本与哈希，进入判定身份；重评同一篇论文用同一份，不重新生成。
- **两步判定**（只用于全局规则）：
  1. 定位：模型看“目录骨架 + 摘要 + 规则”，返回该看哪几个节点（严格 Schema，节点编号用枚举）；
  2. 判定：代码取出这些节点的原文，按现有流程判断与校验引用。
- **必须守住的线**：摘要只用来定位。引用只能来自原文；“论文里没有某内容”不能凭摘要下结论。
- 定位可以按评分项合并为一次（一个评分项的几条全局规则一起定位），见 Q4。
- 摘要要过注入检测；章节角色归类可以顺带挪到论文级别，只做一次。

## 9. 阶段 4：评分助手的按需翻阅

- 给评分助手 Agent 增加三个只读工具：看目录、在论文内搜索、读某一节。
- 只用于人工发起的追问与重判，不进入批量评分，评分权仍为零。
- 与 `docs/评分助手Agent化方案.md` 的工具登记方式一致。

## 10. 存储

| 数据 | 存法 | 理由 |
|---|---|---|
| 章节树 | 不存，读取时由快照拼出 | 形状由原文唯一决定；不动不可变快照的哈希；旧论文立即可用 |
| 目录骨架 | 不存，由树算出 | 同上 |
| 分节摘要、论文级章节角色 | 新表，按“快照 + 节点编号 + 生成版本”存 | 模型生成、需冻结、会随提示词版本变化，不能写进原文快照 |
| 缓存命中 token | 评分用量记录加列 | 计量 |

新建表必须在迁移里给 `pgs_app` 授权并建 RLS。阶段 1 不需要迁移。

## 11. 成本估算（假设值）

假设：论文 4 万 token，40 次语义调用，缓存命中按原价 25% 计。

| 做法 | 折算输入 token |
|---|---|
| 现在：每次约 3 千 token 的片段 | 约 12 万 |
| 全文做前缀，全部命中 | 约 43 万 |
| 全文做前缀，全部未命中 | 160 万 |
| 分层：章节规则给整章、全局规则走摘要定位 | 待用真实规则的范围分布计算 |

结论：全文前缀不采用。分层方案的成本取决于规则在各范围的分布和章节长度，需要先用阶段 2 的计量数据
与一批真实论文算出，再决定章节预算。厂商的折扣比例、最短缓存前缀长度以厂商文档为准，本文未核实。

## 13. 版本与开关

- 改了视图顺序、证据别名与提示词：升 `CORE_PROVIDER_PROMPT_VERSION` 或加后缀；改了选证：升选择器版本，
  `judge-scope@2` 升为 `@3`。决策账本按身份区分，新旧判定不互相复用。
- 压缩器行为变化：升 `COMPRESSOR_VERSION`。
- 摘要与定位各自有提示词版本，进入判定身份。
- 每个阶段一个开关，默认关闭。

## 14. 验证

- 单元测试：拼树（同名标题、缺级标题、无标题论文）、`coverage` 与实际发出内容一致、开关关闭时请求
  逐字节不变、同一范围的两条规则请求前缀逐字一致。
- 迁移自检：新增列与新表（含 `pgs_app` 授权与 RLS）。
- 评测：阶段 1 与阶段 3 改变证据集合，按 §15 QWK 留出集重新锚定。调用真实模型需要单独授权与预算。
- 计量：对比开关前后的输入 token、缓存命中 token、“证据不足”比例、转人工比例。

## 15. 放弃了什么

| 放弃的做法 | 原因 |
|---|---|
| 每条规则都以全文为前缀 | 估算成本是现在的 3 倍以上，且隐式缓存不保证命中 |
| 同一篇论文开一段对话、在末尾不断追加规则 | 后面的判定依赖前面的回答，单条规则无法独立重放，破坏无状态与可复现 |
| 一个评分项的所有规则合并为一次判定 | 规则之间互相影响，一条出错整批重来，决策账本按规则复用的收益丧失；仍列为另行评估 |
| 把树存成节点一行的关系表 | 论文整篇读、整篇用，不需要按节点查询或局部更新；多出的表与迁移没有回报 |
| 把摘要写进论文快照 | 快照不可变且按内容寻址，写入会让旧评分记录的哈希失效 |
| 让模型引用摘要作为证据 | 摘要会丢细节、会出错，逐字引用原文是防编造的核心 |
| 批量评分里让模型多轮自行翻阅 | 成本不可控、路径不可复现；只留给评分助手 |
| 为了前缀去掉 Schema 里的规则编号与证据别名枚举 | 削弱结构化输出的约束，收益未经核实 |

## 16. 风险

- 章节很长时多数仍是 `partial`，缺失类规则会更多转人工；要用真实论文看比例。
- 标题层级解析不准（标题样式不规范的论文）会让树的形状出错；需要“无标题 / 单层标题”的退化路径，
  退化时按全文处理。
- 摘要出错会把定位带偏；定位结果为空或节点不存在时退回 BM25 选证，并记录。
- 定位多一次调用，全局规则多的评分标准成本会上升；按评分项合并可以缓解。
- 隐式缓存是否命中取决于厂商；计量上线前不承诺节省比例。
- 长上下文下模型可能忽略中间内容；整章预算不宜一次放得太大。

## 17. 实施情况（2026-11-15）

已实现（分支 `claude/section-tree-evidence`，全部用合成数据测试，没有调用真实模型）：

| 阶段 | 内容 | 位置 |
|---|---|---|
| 1 | 章节树、目录骨架、位置别名 | `scoring/retrieval/section_tree.py` |
| 1 | 按范围取到的段落原样、按原文顺序发出；字数预算；“整章”按实际发出的内容算（修 P1） | `judge_scope.select_scoped_units` / `scope_view`、`core_view._view` |
| 1 | 目录骨架进请求开头，一篇论文算一次并进入判定身份 | `scope_policy.section_outline`、执行器 `_ScopeExtensions` |
| 2 | 视图顺序改为证据在前、别名按位置（`SCORING_STABLE_PREFIX_ENABLED`） | `core_view._view` |
| 2 | 缓存命中 token 计量 | `llm/usage.py`、三个适配器、迁移 `0045_cached_prompt_tokens` |

与方案的偏离：

- **多了一个范围请求的上下文窗口**（`SCORING_SCOPE_CONTEXT_WINDOW_TOKENS`，默认 14000）。默认窗口的输入预算约
  6000 token，按“1 个汉字约 1 token”的保守估算放不下 Q3 的 8000 字，不加它整章几乎都会被截成“部分”。
- **目录骨架只在有规则要看章节时才带**，不是所有请求都带：这样没有范围规则的评分标准，判定身份不变。
- **范围没有细到小节**。范围仍是章节角色（由 Profile 的词表决定）；要细到小节得改词表与起草提示词，
