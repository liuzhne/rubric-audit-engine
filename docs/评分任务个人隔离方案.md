# 评分任务个人隔离方案

> 状态：已实施（2026-11-10）。§6 的四个问题均按建议确认。

## 1. 要解决什么

现在评分任务、上传的文件和评分结果只按组织隔离：同一组织内的任何组织管理员或教师，都能看到、
改分、导出、删除别人建的任务。评分助手也一样——在自己的对话里问“有哪些任务”，会列出同事的任务。

目标：**教师只能看到并操作自己建的评分任务**，以及任务下的文件、评分结果、复核记录与导出。

## 2. 现状

| 对象 | 归属字段 | 现在按什么判断可见 |
|---|---|---|
| 评分任务 `grading_batches` | `owner_id`、`created_by`（建任务时已写入当前用户） | 只看 `organization_id` |
| 文件 `papers` | `owner_id`（继承任务的归属） | 只看 `organization_id` |
| 评分结果 `scoring_runs` | `owner_id`（继承文件的归属） | 只看 `organization_id` |
| 批量评分作业 | 通过任务 | 只看任务的 `organization_id` |
| v2 提交 `submissions` | `created_by` | 只看 `organization_id` |
| 评分助手对话 | `owner_id` | 已按个人隔离 |
| 评分标准 | `owner_id` + `visibility` | 已有“私有 / 组织”两档 |
| AI 连接 | `owner_id` | 已按个人隔离 |

归属字段早就在写了（模型注释是“P4.3 预留，单租户暂不强隔离”），缺的只是判断。
所以这次**基本不需要新表新列**，改的是守卫和列表查询。

判断散在这些地方：

- `backend/app/api/guards.py`：`visible_batch` / `visible_paper` / `visible_run` / `visible_job`，
  被 batches、papers、scoring、batch_jobs 路由和评分助手（`actions.py`、`assistant/flow.py`、
  `assistant/tools.py`）共用，约 60 处调用。
- 没走共享守卫、自己写了一遍组织判断的：`routes/exports.py`（2 处）、`routes/submissions_v2.py`（4 个 `_visible_*`）。
- 列表与统计：任务列表与工作台概览（`routes/batches.py`）、评分结果列表（`routes/scoring.py`）、
  导出记录（`routes/exports.py`）、需关注的作业（`batch_scoring/jobs.py`）、评分助手查任务（`assistant/tools.py`）。

## 3. 规则

一条规则，所有入口共用：

| 身份 | 能看到 |
|---|---|
| 教师 | 本组织内 `owner_id` 是自己的任务，及其下的文件、结果、作业、导出 |
| 组织管理员 | 本组织内全部（见 Q1） |
| 平台管理员 | 与现在相同 |
| 未开鉴权（本地开发） | 不限制，与现在相同 |

- 看不到的对象一律返回 404，不返回 403——不泄露“这个任务存在”。
- 文件、结果各自有 `owner_id`，但**统一按所属任务的归属判断**，不各判各的：
  一个任务下的东西要么全看得到，要么全看不到，不会出现任务可见而某份文件不可见。
- `owner_id` 为空的旧任务只有管理员能看到（见 Q2）。
- 可见即可操作：改分、复核、重试、取消、删除、导出沿用现有角色判断，不新增“只读”档。

不在这次范围内、保持原样的：

- 评分标准的可见性（已有私有 / 组织两档）。教师仍可用组织共享的评分标准给自己的任务评分。
- 校准锚点（脱敏范文）挂在评分标准上，跟随评分标准可见。
- L0 缓存与规则级决策账本是组织内共用的缓存，没有任何接口能读出别人的内容，继续共用。
- 数据库 RLS 仍只按组织。

## 4. 改动

1. 新增 `services/ownership.py`（归属条件）；`guards.py` 增加 `personal_owner_id` 与三个列表条件，四个 `visible_*` 都改为调用它；
   `visible_paper` / `visible_run` / `visible_job` 先取到所属任务再判断。
2. `exports.py` 与 `submissions_v2.py` 里自己写的判断改为调用共享守卫；v2 的提交与结果按所属
   `evaluation_batches.owner_id` 判断，人工复核任务按所属评分结果的归属判断。
3. 五处列表与统计加上同一个查询条件。工作台概览的数字对教师变成“我的任务”口径。
4. 评分助手不单独改：它的读写已经走同一组守卫，查任务的那一处查询加上同一个条件即可。
5. 迁移 0043：把空的 `owner_id` 回填为 `created_by`，给 `grading_batches` 与 `evaluation_batches` 的
   `owner_id` 加索引。不建新表，不涉及 `pgs_app` 授权。
6. 前端：不改接口。列表自然变短；管理员的任务列表加一列“创建人”（见 Q3）。
   DSH 插件不受影响（路由不变）。
7. 测试：同一组织两个教师互相看不到对方的任务、文件、结果、导出、作业，助手也查不到；
   管理员都能看到；`owner_id` 为空的旧任务教师看不到（`backend/app/tests/test_personal_isolation.py`）。
   没有加 Playwright 用例：隔离全在后端，前端只多一列“创建人”。
8. 三文档同步：ARCHITECTURE（可见性边界）、DECISIONS（见 §5）、RUNBOOK（排错：教师说任务“不见了”，
   先查 `owner_id` 是否为空或是别人的）。

上线前要先查生产库里 `owner_id` 为空的任务有多少（只读查询）；有的话按 Q2 处理后再发布，
否则教师会发现自己的旧任务消失。

## 5. 取舍

- **选了应用层判断，放弃了数据库 RLS 按用户隔离。** RLS 更难绕过，但运行角色是连接池共用的，
  要按用户隔离就得每个请求设会话变量；生产曾因会话级 `SET` 泄漏到 worker 出过事故，
  而且 worker 本来就要跨用户领取任务。代价是：以后新写的接口忘了调守卫就会漏，靠测试兜。
- **选了按任务归属统一判断，放弃了文件与结果各判各的 `owner_id`。** 各判各的少一次查询，
  但三个字段一旦不一致（例如以后做任务转交）就会出现半可见的任务。
- **选了管理员看全部，放弃了“管理员也只看自己的”。** 后者隔离最彻底，但成员离开后其任务再没人能处理。
- **不做任务共享与转交。** 两位教师合评同一任务的需求这次不支持；需要时由管理员处理。

## 6. 已确认的问题（均按建议）

- **Q1 组织管理员是否能看到本组织全部任务？** 建议：能。否则成员离开、任务出问题时没人能接手。
- **Q2 `owner_id` 为空的旧任务怎么办？** 建议：有 `created_by` 的回填为创建人，仍为空的只有管理员可见。
- **Q3 管理员的任务列表是否加“创建人”一列？** 建议：加，否则管理员分不清一堆任务是谁的。
- **Q4 是否需要开关？** 建议：不加，直接生效。隔离要么有要么没有，留开关等于留一条回到“全组织可见”的路。
