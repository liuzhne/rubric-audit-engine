# 评分表结构自动识别方案

> 状态：已确认（2026-11-17，Q1–Q5 按建议执行），实施中。
> 关联：`docs/评分规则解析模块重构方案.md` §5–§8（E1–E9 触发、模型只识别结构、用户确认后合入）。

## 1. 背景

2026-11-17 线上导入一份开题报告评分表（`开题报告评分规则表.xlsx`），页面解析出 23 项、合计 517 分，原表是 22 项、100 分。本地用同一份文件复现，结果一致，原因有三处：

| # | 现象 | 原因（`extraction/table_extractor.py`） |
|---|---|---|
| 1 | 每项满分都是所属一级指标的分值（10,10,10 / 25×5 / 30×5 …） | 表头有两列都叫“分值”：C 列是一级指标分值（纵向合并），E 列是评分项分值。`_find_header` 遇到同名列只取第一列 |
| 2 | 多出一项“合计（满分 100 分）”，满分 100 | 合计行判断要求名称与“合计 / 总分 / 总计”完全相同，带括号说明的写法认不出来 |
| 3 | 每项说明为空，并被设成分档制，分档内容没有意义（如“软件 21001 分”） | 表头“打分规则（分档 / 扣分）”因为包含“分档”两字被映射成 `rubric_levels`，正文被正则拆成档位 |

已有的模型兜底这次没有用上：

- 导入前的“用 AI 识别表格结构”只在整份表解析失败时（报错含“未解析到有效评分项”）出现；这份表解析出了 23 项，算作成功。
- 这份表命中了 E3（序号、一级指标、分值三列有内容但未识别）、E6（覆盖率 42%）、E8（“评分说明”表疑似规则），但这些触发只在评分标准建好后的面板里显示，导入页看不到。
- 最直接的矛盾（标题写“满分 100 分”，合计 517）没有被算成信号：合计行没认出来，E4 不触发。

我们无法预先知道用户会传什么样的表，所以确定性规则总会漏掉一些写法。本方案让系统在**确定性解析后仍有明显矛盾时自动调用模型识别表格结构**，把“当前结果 vs AI 识别结果”的对照交给用户确认。

## 2. 目标与边界

做：

1. 修掉上面三处确定性问题，并让它们产生可检测的信号（§3）。
2. 定义“强信号”：确定性解析之后仍然存在的矛盾（§4）。
3. 导入会话创建后，命中强信号即自动建一次结构识别任务；结果以对照卡片显示，用户采用后才替换草稿（§5、§6）。

不做（保持现有约定）：

- 模型不生成评分项、不改写任何文字。它只输出表头行、列→字段、行类型；文字一律从原表单元格取（`structure_override` 的既有分工）。
- 不在用户确认前修改导入草稿。
- 第二张“评分说明”表里的等级、否决项等全局规则，属于多工作表合并解析，另案处理。
- 已建评分标准的“评分规则”步骤里，现有手动识别面板（`TableRecognitionPanel`）不变。

## 3. 第一部分：确定性修复

| 问题 | 改法 | 交叉校验 |
|---|---|---|
| 同名“分值”列 | 同一字段在表头行命中多列时，不再取第一列。若其中一列在数据区纵向合并、且与某个合并的文字列行范围一致，就把它当作该文字列（维度）的分值；每行独立的那列作为评分项满分。“一级指标”加入维度别名；“二级指标”加入评分项名称别名（排在“指标”之前），两级指标表里二级指标是评分项、一级指标是维度 | 每个维度内各项满分之和 = 维度分值（本表 4+2+4=10 等全部成立）。核对不成立时仍取每行独立的列（最可能正确），但记 `DUPLICATE_SCORE_COLUMN`（E10）；合并特征不明确（没有或有多列每行独立）时保持原选择并记 E10 |
| 合计行 | 名称以“合计 / 总分 / 总计”开头（允许后接括号说明）的行算合计行；名称列合并到分值列的整行也算 | 合计行声明的满分进入 E4 比较 |
| 表头匹配 | 先看完全相同，再看包含；同一列命中多个字段时取最长的别名。“打分规则 / 评分规则 / 评分细则”加入说明列别名 | 映射成 `rubric_levels` 的列，若多数单元格解析不出“档名 + 分数”的整齐结构，降级为说明列 |

另外补一个声明满分的来源：表头区（表头行之前）出现“满分”标签旁的数字，或标题里的“满分 N 分”，记为 `declared_total`。合计行与它都参与 E4。

这部分单独成 PR，不调用模型，只靠测试覆盖。

## 4. 强信号与弱信号

**强信号**：确定性解析后仍然存在的矛盾，只在这些情况下自动识别。

| 编号 | 条件 | 说明 |
|---|---|---|
| E4（扩展） | 解析出的满分合计 ≠ 合计行或表头区声明的满分 | 本表修复前 517 ≠ 100 |
| E10 新增 | 同一字段在表头行命中多列，且 §3 的交叉校验未能确定选哪一列 | 修复后的本表能通过校验，不触发 |
| E11 新增 | 满分列的值在数据区纵向合并（多个评分项共用一个分值单元格） | 典型的“取到了上级分值” |
| E3（收紧） | 未识别用途的列里，数字单元格占多数 | 文字列未识别不算强信号 |
| E9 | 已有：多个评分项共享同一个合并名称，且没能自动转为维度 | 保持 |

**弱信号**：E2、E3（文字列）、E5、E6、E8。只在导入页显示提示和手动入口“用 AI 识别表格结构”，不自动调用。

原则：只有确定性结果“自相矛盾”时才花模型调用；“有些内容没用上”不足以自动调用。阈值是起点，按线上导入记录校准。

## 5. 流程

```
POST /import-sessions（上传）
  └─ 确定性解析 → 计算信号
       ├─ 无强信号：照旧返回会话
       └─ 有强信号且有可用模型
            ├─ 建 AI 任务 structure_suggestion（target = import_session）
            └─ 会话 draft_data.structure_check = {status: running, task_id, signals, state_version}
导入页轮询任务
  └─ 任务成功：按模型结构试解析 → 与当前草稿逐项比较 → 结果存任务
       ├─ 两边一致：卡片显示一行“AI 核对表格结构，结果与当前一致”
       └─ 有差异：显示对照卡片
用户点“采用 AI 识别结果”
  └─ POST /import-sessions/{id}/structure/apply {task_id, state_version}
       └─ 用会话里保存的原文件 + structure_override 重新解析，替换草稿，state_version + 1
```

细节：

- **输入**：复用 `structure_state.import_structure_request`，但文件取自会话已保存的 `rules_file_bytes`，不用重新上传。`failure_codes` 带上命中的信号。现有请求默认只发前 15 行；强信号相关的行（合计行、被丢弃行、合并分值所在行）通过 `extra_rows` 补发，否则模型看不到第 29 行这类合计行。
- **`known_mapping`**：把当前映射发给模型时，去掉被信号指认为可疑的字段（如 `max_score`），避免模型被错误映射带偏。
- **去重**：AI 任务的输入只有原文件解析出的台账与发送内容，不含会话；同一用户重复上传同一文件命中内容指纹，复用的只是模型输出。每个会话各自记录 `task_id` 与建任务时自己的 `state_version`，对照按本会话的草稿重新计算，过期判断也只看本会话，所以复用别的（包括已过期）会话的识别结果不会绕过过期保护。
- **过期保护**：任务记录建任务时的 `state_version`。用户在识别期间改过草稿（删项、改名、改分），采用时 `state_version` 不一致，接口返回冲突，提示“草稿已修改，请重新识别”；人工新增的评分项（没有原表来源、`parse_status=manual`）在替换时保留，排在解析出的评分项之后；页面新增评分项的编号也是 `C%02d`，可能与重新解析出的编号相同，相同时人工项改用下一个空闲的 `C%02d` 编号，名称、分值、说明不变。
- **失败**：模型不可用、超时、两次输出都不合格时，卡片显示原因，并给出手动入口；不影响用户继续使用确定性结果。
- **会话过期**：采用接口只接受待确认的会话；会话取消或过期后，这个会话里的结果不再可采用。

## 6. 对照卡片（导入页）

位置在“解析出的评分项”表格上方。

- 标题写明原因：“表格结构可能识别有误：评分项满分合计 517，与表头声明的满分 100 不一致。”
- 识别中：一行进度和“取消”。
- 识别完成：

| 行 | 评分项 | 满分（当前 → AI） | 所属维度（AI） | 变化 |
|---|---|---|---|---|
| 7 | 封面信息完整 | 10 → 4 | 一、基本信息与论文题目 | 满分 |
| … | … | … | … | … |
| 29 | 合计（满分 100 分） | 100 → — | — | 移除（合计行） |

  底部显示合计：517 → 100（与声明满分一致 ✓）。列映射的变化单独折叠显示，例如“满分取自 E 列（原为 C 列）”“F 列作为说明（原为分档）”。
- 按钮：“采用 AI 识别结果”（主按钮）、“保留当前结果”。保留后卡片收起，可以再次展开。

对照只展示代码按模型结构从原表取出的数据，不展示模型自己写的文字；每项判断的依据（`reason`）放在折叠区，供核对。

## 7. 数据与接口

- **不建新表，不加迁移。** 状态放在导入会话的 `draft_data.structure_check`（JSON）；AI 任务 `rubric_id` 为空（0037 已允许），任务输入快照只有台账与发送内容；会话与任务的对应关系、建任务时的 `state_version` 记在会话的 `structure_check` 里。
- **AI 任务**：`structure_suggestion` 增加 `target = "import_session"`；处理器复用 `import_structure_preview`，再加一步与会话草稿比较（复用 `reupload_diff` 的比较逻辑）。可见性沿用导入前识别：只有会话所有者可见。
- **接口**：
  - `POST /import-sessions` 响应增加 `structure_check`（`none | running | consistent | differs | failed | dismissed`，以及 `signals`、`task_id`）。
  - `POST /import-sessions/{id}/structure/apply`：采用识别结果。
  - `POST /import-sessions/{id}/structure/dismiss`：保留当前结果。
  - 都要更新 OpenAPI 合同（`api:dump && api:check`），前端契约版本随之升级。
- **提示词**：`failure_codes` 会出现新编号，且补发行的方式变化，升 `STRUCTURE_PROMPT_VERSION` 到 `rubric-structure@3`。
- **开关**：`IMPORT_STRUCTURE_AUTO_ENABLED`，默认关闭；上线核对后再打开。

## 10. 分期

1. **PR A：确定性修复 + 新信号**（§3、§4）。不调用模型，可以先上线；本表重新上传后即可得到正确结果。
2. **PR B：自动识别 + 对照卡片**（§5–§7）。开关默认关闭。

两份 PR 都开到 `develop`，同步 ARCHITECTURE / DECISIONS / RUNBOOK。DECISIONS 记录放弃的方案：

- 让模型直接生成评分项：放弃，原因是可能改写或编造规则，同一份表重复导入结果也不稳定。
- 每次导入都调用模型：放弃，大多数表没有矛盾，白白产生费用和等待。
- 弱信号也自动调用：放弃，“内容没被用上”常常是签字栏、表头说明这类正常情况。

## 11. 实施记录（2026-11-17）

- PR A（确定性修复 + 强信号）与 PR B（自动识别 + 对照卡片）均开到 `develop`；PR B 叠在 PR A 之上。
- 用 2026-11-17 线上那份 Excel 本地验证：修复后解析出 22 项、合计 100、6 个维度，说明列有内容；强信号为零，不会触发自动识别（只剩“序号”列与“评分说明”表两个弱信号）。
- 与方案的偏差：
  - §3：同名分值列核对不通过时，仍取每行独立的列并记 E10（原写“不自动选择”）。理由见 DECISIONS。
  - §5：识别结果不在任务成功时回调写会话，而是读取会话时按任务状态推导、第一次读到成功结果就缓存进会话。
  - Q3：已建评分标准重新上传走现有的“草稿结构建议”任务与面板，没有另做对照卡片。
- 未做：真实模型对这类表的识别效果评测（需要授权与预算）。
