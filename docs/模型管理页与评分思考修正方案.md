# 模型管理页与评分思考修正方案

状态：Accepted（2026-11-17 维护者确认）：Q1 只限平台管理员；Q2 同意第一期规则，不先跑 QWK；Q3 Agent 评测状态只读；Q4 两期分两个 PR。

## 1. 现象

2026-11-17 00:45 的评分任务“助手评分 · 7 份”（开题报告-2026-2027，连接为智谱 `glm-5.3`）7 份全部失败，错误码是 `PROVIDER_THINKING_NOT_DISABLED`。每份大约输入 1500、输出 2048 token，其中思考约 2030 token，截断 1 次。

## 2. 根因

能力表其实记着这个模型的能力：`glm-5.3` 强制思考，关不掉，只能发 `reasoning_effort: low`（`thinking_capabilities.py`，2026-11-10 核实）。问题在于**评分路径不读这张表**：

- `THINKING_CAPABILITY_SCOPE` 默认是 `auxiliary`，只有 AI 任务和评分助手按能力表发思考参数。评分路径（`plans()` 返回的评分计划）仍走旧行为 `legacy_chat_plan`。
- 旧行为在智谱主机上原样使用连接或全局的 `thinking_type`，默认是 `disabled`，所以运行身份记成“不思考”，输出上限也沿用 2048。
- 模型实际在思考，`batch_scoring/jobs` 观测到推理 token 后按约定停掉整个任务。这一步本身是对的：运行身份和实际行为不一致，评分不可复现。

所以只加一个模型管理页解决不了这次的报错：表里已经写对了，是评分路径没有用它。另一方面，今后厂商每上一个新模型都要改代码、走发布，管理员没法自己补登记——这才是模型管理页要解决的问题。

## 3. 方案

分两期。第一期不建表，先止损；第二期做管理员页面。

### 3.1 第一期：评分路径遵守“关不掉”的记录（不建表、无迁移）

**规则**：`plans()` 仍按 `THINKING_CAPABILITY_SCOPE` 选择评分计划。但如果旧行为判定“思考关闭”，而能力表明确记着这个模型**关不掉思考**（`can_disable=False`），评分计划就改用能力表的计划：

- 发最低思考强度（`glm-5.3` 发 `reasoning_effort: low`）；
- 运行身份如实记为开启（`provider-default` + `effort=low`）；
- 输出上限放到封顶值（`min(模型最大输出, 32768)`），连接上显式填写的上限仍然优先。

**为什么不需要先跑 QWK**：这条规则只影响“旧行为必定失败”的模型。它们现在一份都评不出来，没有可以回归的基线。能关闭思考的模型、表里没有记录的模型、以及 `SCOPE=all` / `off` 下的行为都不变。

**缓存与账本**：这些模型的运行身份会变（多出 `;effort=low;max_tokens=…`），旧判定不会被复用。旧判定本来也没有一条成功，所以没有损失。

**同时修改**：

- 失败提示 `THINKING_NOT_DISABLED_MESSAGE` 分两种情况。表里已有记录却仍然观测到思考时，说明记录写错了，提示转告管理员核对；表里没有记录时，提示管理员在“模型管理”里登记。
- 连接的“测试”按钮本来就会发一次请求。应答里有推理 token 时，在测试结果里注明“这个模型会思考”；表里没有它的记录时，再提示联系管理员登记。不额外发请求。

### 3.2 第二期：管理员的模型管理页（迁移 `0047_model_capability_overrides`）

**数据**：新表 `model_capability_overrides`，全平台共享，不按组织区分。模型的能力是厂商定的事实，和是哪个学校在用无关。

| 字段 | 说明 |
|---|---|
| `id`、`protocol`（chat / responses / messages）、`host_family`、`model_prefix` | 匹配键，含义与代码里的能力表相同 |
| `can_disable`、`off_request`（JSON）、`lowest_effort`、`effort_request`（JSON）、`max_output_tokens` | 与 `ThinkingCapability` 一一对应 |
| `enabled`、`note`、`source_url`、`verified_on` | 停用即退回代码表；来源链接必填 |
| `created_by`、`updated_by`、`created_at`、`updated_at`、`revision` | 审计与乐观锁 |

按约定，迁移里给 `pgs_app` 授权并建 RLS（照 0023 的做法）。降级时，表里有数据就拒绝。

**解析顺序**：连接的显式配置 → **数据库记录** → 代码能力表（具体前缀 → 族默认）→ 未知模型策略。数据库记录与代码记录比较前缀长度，最长的胜出；长度相同时数据库记录优先。

**生效方式**：app 与 worker 进程内缓存全部启用的记录，每 30 秒检查一次（记录数, `max(updated_at)`, `sum(revision)`），任何一项变了就重新读取（每次修改都会让 `revision` 加 1，求和才能保证任一条记录改动都被发现；只看 `max(revision)` 时，别的记录版本更高就看不出变化，#115 复审）。写入接口提交后立刻让本进程的缓存失效。新任务最迟 30 秒后用上新记录；已经在跑的任务不受影响，因为它的适配器在开始时已经算好了计划。

**运行身份**：沿用“改了写法就要换身份”的规则。命中数据库记录时，在 `model_version` 后面追加 `;cap=<记录内容哈希前 8 位>`，改了记录就不会复用旧判定。

**请求写法的白名单**：`off_request` 和 `effort_request` 只接受 `thinking`、`reasoning_effort`、`reasoning`、`extra_body`、`output_config` 这几个顶层键，嵌套不超过 4 层，大小不超过 1 KB。管理员不能借这里往请求里塞任意字段（比如 `model`、`messages`）。

**页面**：

- 左侧菜单的“运维”分组下新增“模型管理”，只有平台管理员（`view_platform_ops`）能看到。
- 列表合并展示代码表和数据库记录，标明来源（代码 / 管理员登记）、能否关闭思考、最低强度、最大输出、核实日期、来源链接，以及助手 Agent 评测状态（只读，见 Q3）。
- 代码记录不能删除，只能“覆盖”：以它为底稿新建一条数据库记录。数据库记录可以编辑和停用。
- 保存前预览这条记录会发出的请求字段，以及哪些现有连接会受影响（按协议、主机族、前缀统计启用中的连接数）。
- 每次写入记一条审计事件。

**接口**：`GET/POST /api/v1/admin/model-capabilities`、`PATCH /…/{id}`（带 `revision`），全部要求 `require_platform_admin`。前端契约版本照常升级。

## 4. 放弃了什么

- **把能力表整体搬进数据库**：会丢掉代码评审和写法快照测试（`test_thinking_capabilities`），而这张表的每一条都影响运行身份。所以代码表保留为默认值，数据库只做覆盖。
- **直接把 `THINKING_CAPABILITY_SCOPE` 切到 `all`**：这会改变所有模型的评分身份，包括现在能正常评分的模型，按约定要先跑 QWK。第一期只放开“必定失败”的那一类模型。
- **自动探测**（每个新模型先发一次请求，看它会不会思考）：每次都要花钱，结论也不稳定（有的模型思考与否取决于题目）。只在用户本来就会点的“测试”里顺带观察。
- **让组织管理员编辑**：能力是全平台共享的事实，一个学校改错会影响所有学校（见 Q1）。
- **把 Agent 的评测名单也做成可编辑**：部署门槛 `assistant_eval_gate` 要求名单里的每个模型都有达标评测；页面上一勾就放行，等于绕过这个门槛（见 Q3）。

## 6. 测试

- 第一期：`test_thinking_capabilities` 增加 `glm-5.3` 在 `auxiliary` 范围下的评分计划用例（强制低强度、身份记开启、上限放开）；能关闭思考的模型、未知模型和 `off` 范围下评分计划不变（逐字节快照）；`test_batch_scoring` 中智谱 `glm-5.3` 的替身不再触发 `PROVIDER_THINKING_NOT_DISABLED`。
