## 1. 背景

### 1.1 这次失败是怎么发生的

- GLM-5.3 关不掉思考（智谱文档：强制思考，传 `thinking.type=disabled` 会报错）。强度只能用 `reasoning_effort` 调，取值 `max`（默认）/ `high` / `low`。
- 这条连接没有配置思考。`thinking_params.thinking_request_fields` 对非 Google 主机只会发 `thinking.type`，没配置就什么都不发，模型于是按默认的 `max` 强度思考。
- 起草的输出上限是 `max(连接上限 2048, 6144) = 6144`（`ai_rule_drafter` 第 697–700 行）。思考 token 计入这个上限，思考还没写完，额度就用光了。

### 1.2 差异散落在哪里

同一协议下各厂商的差异，现在按主机名和模型名在三处特判：

| 位置 | 判断什么 | 问题 |
|---|---|---|
| `llm/thinking_params.py` | Google 主机 + `gemini-2.5-flash*` 名单 | 只有 Google 一家；名单之外一律「不发」 |
| `llm/auth_headers.py` | Vertex 主机换鉴权头 | 与思考无关，但主机识别各写一份 |
| `openai_compatible_adapter.complete_json` | `openrouter.ai` 上带 Schema 时发 `reasoning.enabled=false` | 只在起草路径生效 |
| `anthropic_messages_adapter.request_controls` | 只发连接显式配置的 `thinking` / `effort` | 没配置时完全交给模型 |
| `openai_adapter`（Responses） | 不发任何思考参数；Core 信封遇到思考身份直接拒绝 | OpenAI 推理模型在 Core 评分里被挡住 |

### 1.3 没配置思考时，现在发什么、身份记什么、实际怎样

| 连接 | 现在发出的思考参数 | 运行身份 `thinking` | 模型实际 |
|---|---|---|---|
| Chat · Vertex / Gemini API · 2.5 Flash | 关闭写法 | `{false, "none"}` | 不思考，如实 |
| Chat · Vertex / Gemini API · 2.5 Pro、Gemini 3 | 不发 | `{true, "provider-default"}` | 按默认强度思考，如实 |
| Chat · 智谱 GLM-5.2 | 不发 | `{false, null}` | 默认开着思考，**身份不实**（Core 评分被守卫拦下） |
| Chat · 智谱 GLM-5.3 | 不发 | `{false, null}` | 强制思考、`max` 强度，**身份不实**（11-10 事故） |
| Responses · OpenAI 推理模型 | 不发 | `{false, null}` | 按默认强度思考，**身份不实**（Core 被拦） |
| Claude · Opus 5.5 / 5、Sonnet 5.5 / 5、Haiku 5.5 | 不发 | `{false, null}` | 省略 `thinking` 时默认 adaptive 思考，**身份不实** |
| Claude · Opus 4.6–4.8、Sonnet 4.6、Haiku 4.5 | 不发 | `{false, null}` | 省略即不思考，如实 |

「身份不实」的连接在 Core 评分里会被 `ThinkingConsistencyGuard` 拦下（P1 的设计），在 AI 任务里则按默认强度思考、撞上输出上限。

## 2. 用户已定的规则（2026-11-10）

1. **能关闭思考的模型**：直接关闭，输出上限沿用现有值。
2. **关不掉思考的模型**：默认发最低思考强度；不给思考设 token 上限，只限制正式输出。
3. **改动放在适配器层**：由代码识别模型能不能关、怎么关、最低强度怎么发。

## 3. 能力表

### 3.1 位置与结构

新模块 `backend/app/services/llm/thinking_capabilities.py`，是一张静态表加一个查找函数。每条记录：

```python
ThinkingCapability(
    families=("zhipu",),            # 主机族，见 3.2
    model_prefix="glm-5.3",         # 规整后的模型名前缀，见 3.3
    can_disable=False,              # 能不能关闭思考
    off_request=None,               # 关闭思考的请求写法（合并进请求体的 JSON 片段）
    lowest_effort="low",            # 最低强度的名字（进运行身份，见第 6 节）
    effort_request={"reasoning_effort": "low"},  # 最低强度的请求写法
    max_output_tokens=128_000,      # 模型的最大输出 token
    sources=(                        # 来源链接，至少一条
        "https://docs.bigmodel.cn/cn/guide/capabilities/thinking.md",
        "https://docs.z.ai/guides/overview/migrate-to-glm-new",
    ),
    verified_on="2026-11-10",       # 核实日期
)
```

- 写法是「合并进请求体的 JSON 片段」，不是枚举。各家的形状差得很远（`thinking.type`、`reasoning_effort`、`extra_body.google.thinking_config`、`reasoning.effort`、`output_config.effort`、通义的 `enable_thinking`），片段能装下所有形状，适配器只负责合并。
- `off_request` 可以是空片段 `{}`，表示「省略即关闭」（例如 Claude Opus 4.7/4.8：不发 `thinking` 就不思考）。
- 它**取代** `thinking_params.google_can_disable_thinking` 的名单。`thinking_params` 只保留旧路径的换算函数（第 4.4 节），内部改为查表。
- 表不进连接快照：否则改一条记录，所有锁定了连接的在跑任务都会报 `AI_CONNECTION_CONFIG_CHANGED`（与 P3 不把探测结果放进快照同一个理由）。

### 3.2 主机族

主机识别集中成一个函数 `host_family(base_url)`，`auth_headers.is_vertex_host` 改为调用它（鉴权头本身不进能力表，它与思考无关）。

| 主机族 | 主机 | 协议 |
|---|---|---|
| `vertex` | `aiplatform.googleapis.com`、`<区域>-aiplatform.googleapis.com` | Chat |
| `gemini_api` | `generativelanguage.googleapis.com` | Chat |
| `zhipu` | `open.bigmodel.cn`、`api.z.ai` | Chat |
| `openrouter` | `openrouter.ai` | Chat |
| `dashscope` | `dashscope.aliyuncs.com`、`dashscope-intl.aliyuncs.com` | Chat / Responses |
| `deepseek` | `api.deepseek.com` | Chat |
| `moonshot` | `api.moonshot.cn`、`api.moonshot.ai` | Chat |
| `openai` | `api.openai.com` | Responses / Chat |
| `anthropic` | `api.anthropic.com` | Claude |
| `bedrock` | `bedrock-runtime.<区域>.amazonaws.com`、`bedrock-mantle.<区域>.api.aws` | Claude |
| `other` | 其余（含本地与自建网关） | 任意 |

同一个模型在不同主机上写法不同（Gemini 2.5 Flash 关闭思考：Vertex 发 `thinking_budget=0`，Gemini API 发 `reasoning_effort: none`，OpenRouter 发 `reasoning.enabled=false`），所以记录按「主机族 + 模型名前缀」匹配，只按模型名不够。

### 3.3 模型名规整与匹配

模型名由老师自由填写，先规整再匹配：

1. 去掉首尾空白，转小写；
2. 取最后一个 `/` 之后的部分（`google/gemini-2.5-flash`、`models/gemini-2.5-flash`、`z-ai/glm-5.3`）；
3. Bedrock 的推理配置文件前缀去掉，取 `anthropic.` 之后的部分（`global.anthropic.claude-opus-5-5`、`us.anthropic.claude-sonnet-4-6-v1:0`）。

匹配规则：

- 在同一主机族的记录里找所有前缀命中的，**取最长的那个**（`gemini-2.5-flash-lite` 优先于 `gemini-2.5-flash`）。
- **前缀必须落在版本号的边界上**：前缀后面紧跟的若是版本号的延续——数字、`.数字`、`-一到两位数字`——不算命中。所以新出的 `claude-opus-5-6` 不会继承 `claude-opus-5` 的记录、`gpt-5.1` 不会命中 `gpt-5`，而是落到未知模型策略。日期快照（`-20251001`、`@20251101`）和变体后缀（`-lite`、`-preview-09-2025`、`-v1:0`、`-flash`）算命中。
- 主机族可以有一条空前缀的**族默认记录**（目前只有 OpenRouter，见第 10 节），优先级低于任何具体前缀。

## 4. 解析顺序

### 4.1 三层

```
连接的显式配置  →  能力表（具体前缀 → 族默认记录）  →  未知模型策略（Q1）
```

| 层 | 什么算「有」 | 结果 |
|---|---|---|
| 显式配置 | Chat 的 `provider_options.thinking_type` 非空；Claude 的 `thinking_type` 或 `effort`；不走连接的平台环境变量 `OPENAI_COMPATIBLE_THINKING_TYPE` | 原样发出（与现在相同），只在 Q4 的冲突情形例外 |
| 能力表 | 命中记录 | 能关 → `off_request`；关不掉 → `effort_request` |
| 未知模型 | 两者都没有 | 按 Q1 |

### 4.2 解析结果

解析函数 `resolve_thinking(protocol, base_url, model_name, *, thinking_type, effort)` 返回一个不可变的计划，适配器在构造时算一次：

```python
ThinkingPlan(
    thinking_on=True,                 # 可能在思考：决定运行身份的 enabled 与输出上限
    identity_type="provider-default", # 运行身份的 thinking.type（第 6 节）
    effort="low",                     # 发出的强度；没发为 None
    request_fields={"reasoning_effort": "low"},
    source="table",                   # explicit / table / family_default / unknown / legacy
    entry="zhipu:glm-5.3",            # 命中的记录；未知为 None
    model_max_output_tokens=128_000,  # 表里有才有
)
```

### 4.3 作用范围与开关

新增环境变量 `THINKING_CAPABILITY_SCOPE`（取值见 Q3，推荐默认 `auxiliary`）：

| 取值 | AI 任务（起草、归类、审查、结构识别）与评分助手 | 评分路径（Core 规则评分、旧兼容路径、语义一致性检查） |
|---|---|---|
| `off` | 旧行为 | 旧行为 |
| `auxiliary` | 能力表 | 旧行为 |
| `all` | 能力表 | 能力表 |

`off` 用于不发版回滚。实现上适配器持有两份计划：`thinking_plan`（给 `complete_json` / `complete_with_tools`）和 `scoring_thinking_plan`（给 `score_*`；`all` 时与前者相同，否则是旧行为）。语义一致性检查走 `complete_json`，加一个关键字参数 `scoring=True` 让它用评分路径的计划。

### 4.4 「旧行为」精确是什么

`scoring_thinking_plan` 在非 `all` 时必须与改动前**逐字节相同**（请求体与运行身份都一样），用黄金测试锁住（第 11 节）：

- Chat：`effective_thinking_type` + `thinking_request_fields`，只是 Google 名单改为查表里 Google 族的 `can_disable`。表里 Google 族的 2.5 Flash 记录与原名单等价，行为不变。
- Claude：只发显式配置（`request_controls` 原样）。
- Responses：不发思考参数。

## 5. 「只限制正式输出」怎么落地

### 5.1 上限把思考算在内

各家的输出上限都把思考 token 算在内：

| 厂商 | 依据 |
|---|---|
| 智谱 GLM-5.3 | 生产日志 2026-11-10：起草 6144 用光，`finish_reason=length` |
| Vertex Gemini | 生产日志 2026-10-19：48 次调用推理 46,463 token、5 次撞上 2048 截断；Gemini 文档「`max_output_tokens` applies to the combined total of thinking tokens and output tokens」 |
| OpenAI | 推理指南：`max_output_tokens` 限制模型生成的全部 token，含推理 token |
| OpenRouter | 推理文档：上限同时作用于推理与可见输出 |
| Claude | 思考 token 计入 `output_tokens` 与 `max_tokens`（适配器已按此处理截断） |

所以对思考开着的请求，请求里的上限不能当「正式输出上限」用。

### 5.2 请求上限怎么定

调用方今天传的 `default_max_tokens` / `max_tokens`（起草 6144、归类与结构识别 8192、助手每步 1200、意图识别 300）一律改称**正式输出预算**，含义不变，只是不再直接作为请求上限：

| 计划 | 请求里的上限 |
|---|---|
| 思考关闭 | 与现在相同（各方法现有的取法不变，例如 `complete_json` 是连接显式上限优先，否则 `max(连接上限, 正式输出预算)`） |
| 思考开着（关不掉、显式开启、未知模型） | 连接显式上限优先；否则 `min(模型最大输出, 项目封顶)`，表里没有最大输出时取项目封顶（Q2，推荐 32,768） |

连接显式上限仍然优先：老师写了就照发。代价是关不掉思考的模型配了很小的上限会截断，截断提示据此改写（8.4）。

### 5.3 正式输出靠什么约束

请求上限放开之后，正式输出的长度靠输出结构的上界和提示词约束：

| 调用 | 正式输出的上界 | 够不够 |
|---|---|---|
| 起草 | 严格 Schema：每批最多 2 组、每组最多 3 条、文字 ≤ 320 字、来源 ≤ 6 条 | 够。精简 Schema 回退时没有上界，只剩提示词里的同样要求 |
| 归类 | 每批 3 个原文单元，每个单元一条归类 | 够（条数固定） |
| 结构识别 | 输入按字符预算截断，输出是表头映射 | 够 |
| 审查 | 只有提示词 | 不够硬，但输出是问题列表，一般很短 |
| 评分助手 | 每步一次工具调用或一段回复 | 够 |
| Core 规则评分（`all` 时） | 目前没有 `maxItems` / `maxLength`（输出预算方案 G3） | **不够**：要等 P2 的有界输出契约。这也是 Q3 推荐评分路径先不生效的原因之一 |

本方案不改任何提示词与 Schema。

### 5.4 事后记录正式输出用了多少

- 调用日志 `llm_call` 行尾加 `thinking=off|on`、`effort=`、`answer_tokens=`、`answer_budget=`（正式输出预算）、`max_tokens=`（实发上限）。不含任何内容。
- `answer_tokens` 只在算得出来时记，算不出来记 `-`，不猜：
  - 厂商报告了推理 token，且合计 = 输入 + 输出（推理算在输出里，OpenAI、OpenRouter）：`completion − reasoning`；
  - 合计 > 输入 + 输出（推理不算在输出里，Vertex）：`completion`；
  - 没有推理计数（智谱只给 `reasoning_content`、Claude 只给思考块）：`-`。
- 第一期只进日志，不加迁移；运维页要看趋势时再加列。
- 计划为「关闭」、却观测到思考时，另记一行 `thinking_capability_mismatch family=… model=… entry=…`。AI 任务没有一致性守卫，这一行是发现能力表误标的主要途径。

### 5.5 真正的上限变成了时间

请求上限放开以后，一次调用最终被超时截住：

- **单次超时**：连接显式 `timeout_seconds`（1–300）优先。没显式配置时，AI 任务今天的缺省等待是 120 秒；思考开着的计划改为 Q2 的值（推荐 240 秒），关闭的仍是 120 秒。
- **与截止时间配合**：`transport.post_with_retry` 每次尝试的超时取 `min(单次超时, 截止时间 − 现在)`，规则不变。AI 任务的条目不传截止时间（`deadline=None`），所以由单次超时决定；评分助手每步 20 秒、意图识别 30 秒的截止时间照旧压住单次超时。
- **超时之后**：
  - AI 任务：传输层只试 1 次（`attempts_limit=1`），条目层按 `request_timeout` 再执行 1 次（现有处理方式），仍超时就失败。提示在思考开着时改为「这个模型关不掉思考，已按最低强度 `low` 请求，仍在 N 秒内没有返回；可以在连接里把超时调到最多 300 秒，或换能关闭思考的模型」。
  - 评分助手：现有的「退回规则模式」不变。关不掉思考的模型多半挤不进 20 秒一步，会更常退回；平台模型目前是 Gemini 2.5 Flash（能关），不受影响。
  - 评分路径（`all` 时）：规则失败的现有处理不变，恢复策略属于 P2。
- **花费**：超时的请求，厂商多半仍按已生成的 token 计费；单次最坏花费由项目封顶决定（Q2）。
- worker 的条目租约靠每 15 秒一次的心跳续期，长调用不会被巡检当成死掉。

## 6. 运行身份

### 6.1 现状

`core_runtime_provider_contract` 冻结的 `thinking` 只有两项：`enabled` 与 `type`。信封契约 `contracts._normalize_provider` 要求二者一致：`type` 为空或属于 `{disabled, none, false, off}` 时 `enabled` 必须为 false，否则必须为 true。`provider` 是封闭结构，不能加字段。Claude 的做法是把 effort 写进 `model_version`（`messages-2023-06-01;effort=low`）。

### 6.2 做法：`type` 记开关，强度记在 `model_version`

不改封闭结构，三个适配器统一沿用 Claude 的先例：

- `thinking.type` 只表示**开关**：
  - 关闭：Google 族记 `none`、其余记 `disabled`（都是现有的值）；「省略即关闭」的（Claude 4.6–4.8、非推理的 OpenAI 模型）照旧记 `null`；
  - 关不掉、未知模型、或显式开启但没发开关参数：记 `provider-default`（现有的值）；
  - 显式配置的其它值（`enabled`、`adaptive`）原样记。
- 发了强度，就在 `model_version` 末尾加 `;effort=<级别>`：`chat-completions;effort=low`、`responses-api;effort=minimal`、`messages-2023-06-01;effort=low`。
- 写法不进身份：同一模式在不同主机上的写法由能力表翻译。一个快照测试把「每条记录 × 每种模式 → 请求片段」冻结下来；**改了某条记录的写法，必须同时改它的身份值（换强度名）或升 `CORE_PROVIDER_PROMPT_VERSION`**，测试失败时的提示写明这条规矩。

为什么不把能力表的版本写进身份：那样表一改，所有连接的账本一起失效，包括写法根本没变的生产平台模型（Gemini 2.5 Flash）。

### 6.3 改动前后的身份

原则：请求写法没变，身份不变；写法变了，身份一定变；原来的身份是不实的，也要变。

| 连接（没配置思考） | 改动前 | 改动后 | 账本与缓存 |
|---|---|---|---|
| Vertex · Gemini 2.5 Flash（生产平台模型） | `{false,"none"}`，`chat-completions` | 不变 | 继续复用 |
| 智谱 GLM-5.2 | `{false,null}`，不发参数 | `{false,"disabled"}`，发 `thinking.type=disabled` | 失效一次 |
| 智谱 GLM-5.3 | `{false,null}` | `{true,"provider-default"}`，`chat-completions;effort=low` | 失效一次 |
| Vertex · Gemini 2.5 Pro / 3 | `{true,"provider-default"}` | 同左，`model_version` 加 `;effort=low`（3 Flash 为 `minimal`） | 失效一次 |
| Claude Opus 5.5 | `{false,null}` | `{true,"provider-default"}`，`messages-2023-06-01;effort=low` | 失效一次 |

以上只在对应路径启用能力表时生效：AI 任务没有运行身份；评分路径要到 `all`。

### 6.4 版本号

- `CORE_PROVIDER_PROMPT_VERSION`：**不升**。提示词没变；该变身份的连接身份已经变了，账本与 Core 缓存自然不复用；写法没变的连接本来就应该继续复用（同 2026-10-16 条的理由）。
- `llm_cache.PROMPT_VERSION`：**评分路径接入时升一次**。旧兼容路径的 L0 缓存键（`cache/llm_cache.build_request`）不含思考设置与输出上限，GLM-5.2 从「不发」变成「发 disabled」时 `model_version` 不变，旧键会命中旧结果。做法是把 `thinking` 计划与实发上限加进缓存键，同时升版本号；以后改思考写法不必再记得升。
- AI 任务的内容指纹只用于在途任务去重，不受影响。

### 6.5 Core 的证据预算（只在 `all` 时）

`thesis.py` 第 769 行与 `technical_proposal.py` 的同一处，把 `provider.sampling.max_tokens` 当作输出预留，从上下文窗口 `SCORING_CONTEXT_WINDOW_TOKENS=9040` 里扣掉。思考开着时实发上限是 32,768，直接扣会让输入预算变成负数。改为扣**正式输出预算**（连接配置的上限，默认 2048）；实发上限只进 `sampling.max_tokens`。这会改变证据选择的身份，属于评分变化，跟着 Q3 走。

## 7. `ThinkingConsistencyGuard`

语义不变：运行身份写着「关闭思考」（`enabled=false`），却观测到思考，就停下（本篇失败、同任务未开始的材料取消，错误码 `PROVIDER_THINKING_NOT_DISABLED`）。

- 能力表把某个模型误标成「可关闭」时，身份会写关闭、模型却在思考，正好由它兜住；错误提示加一句「可能是能力表把这个模型记成了可以关闭思考」，RUNBOOK 写明怎么查是哪条记录。
- 计划为思考开着时身份是 `enabled=true`，守卫不核对，这与现在 `provider-default` 的处理相同。
- AI 任务不经守卫（与现在相同），误标靠 5.4 的 `thinking_capability_mismatch` 日志发现。

## 8. 三个适配器与调用方要改的地方

### 8.1 Chat（`openai_compatible_adapter.py`）

## 13. 放弃了什么

- **只按模型名匹配**：同一模型在 Vertex、Gemini API、OpenRouter 上的写法不同。
- **先做 P3 探测再定写法**：探测要真实调用模型、要预算授权，而且探测只能告诉我们「请求关闭后还在不在思考」，给不出「最低强度怎么写」。先用有来源的表，探测以后用来核对表。
- **让老师在连接里填 `reasoning_effort` 或请求片段**：用户的规则是由代码识别；表单、校验和身份字段都要改，老师也不该知道各家写法。
- **对关不掉的模型继续「不发参数、靠上限兜底」**（2026-10-16 的做法）：GLM-5.3 默认 `max` 强度，靠上限兜不住，11-10 的失败就是这样。
- **用思考 token 预算（`thinking_budget`）代替强度**：用户规则是不给思考设 token 上限；Gemini 的预算本身也只是参考值，Gemini 3 已改用强度档位。
- **扩展信封的 `thinking` 结构加一个 effort 字段**：要改封闭契约和信封版本，已保存的结果与回放校验都受影响；Claude 已有把强度写进 `model_version` 的先例。
- **把能力表版本写进运行身份**：表一改，写法没变的连接也会丢掉账本复用；改用写法快照测试加「改写法必须换身份」的规矩。
- **改用流式以便超时时拿到部分结果**：改动大，半截 JSON 也用不了。
- **请求上限用模型官方最大输出**：见 Q2。
